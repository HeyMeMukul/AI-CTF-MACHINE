## ECC / DSA family

### W13 — HNP lattice with explicit K-scaling and sample-count rule
- Condition: `m` ECDSA/DSA signatures `(r_i,s_i)` on known hashes `h_i`, each nonce `k_i`
  bounded by `2^B` with `B` well under `n_bits` (MSB leak, LSB leak, or small-nonce RNG).
  Need roughly `m >= n_bits / leaked_bits` samples (e.g. 256-bit curve, 8-bit leak needs
  a few dozen; 4-bit leak needs low hundreds); below that no tuning helps.
- Steps: 1. Reduce each sig to `k_i = t_i*d + a_i (mod n)` with `t_i = s_i^-1*r_i`,
  `a_i = s_i^-1*h_i`. 2. Build `(m+2)x(m+2)` basis: diagonal `n` block, one row of `t_i`,
  one row of `a_i`, scale last two rows by `K = 2^B` so the planted vector is shortest.
  3. LLL, scan rows for candidate `d = round(row[m]*n/K) mod n`. 4. Verify EVERY candidate
  via `d*G == Pub` (also try `n-d`); on failure try Babai nearest-plane / BKZ before
  declaring under-sampled.
- Snippet: ```python
  from sage.all import *
  def hnp_candidates(t, a, n, B):
      m = len(t); K = 2**B
      M = Matrix(QQ, m+2, m+2)
      for i in range(m): M[i,i] = n
      for i in range(m): M[m,i] = t[i]; M[m+1,i] = a[i]
      M[m,m] = K/n; M[m+1,m+1] = K
      for row in M.LLL():
          yield int(round(row[m]*n/K)) % n
  ```
- Pitfalls: unscaled lattice returns short-but-wrong vectors (most common time sink);
  MSB vs LSB leak flips which rows carry modulus vs bound weight; identical-`r` pairs mean
  plain reuse (no lattice needed); endianness of `h_i` (bytes vs int) breaks all rows.
- Sources: https://sinapsi.wiki/w/ctf-crypto/p/signatures/dsa-nonce-bias-lattice/ ,
  https://ctftime.org/writeup/32659 , https://ctfbase.com/writeup/20240531_gpnctf_easy_dsa

### W14 — ECDSA polynomial-nonce recurrence (related-nonce elimination)
- Condition: nonces generated by secret polynomial LCG `s_i = f(s_{i-1})` of known degree
  (e.g. degree 7) over prime field, tokens `t_i = x*(s_i+u_i)^-1` leak per-user; enough
  samples to eliminate coefficients (>= degree+1 equations plus unknowns).
- Steps: 1. Write each nonce as `s_i = x*t_i^-1 - u_i`. 2. Substitute into the `P`
  recurrence equations; coefficients appear linearly so eliminate them (Algorithm 2 of the
  related-nonce paper), leaving one high-degree equation in `x` only. 3. Root-find over
  the prime field, back-substitute for coefficients, predict the next token and verify
  against a known registration before forging.
- Snippet: ```python
  # Sage sketch: eliminate a0..a7 from P-equations, solve for x only
  R = PolynomialRing(GF(N), 'x'); x = R.gen()
  # s_i(x) = x*inv(t_i) - u_i ; substitute into s_{i+1} - f(s_i) == 0, eliminate
  # polys = [...]; G = Ideal(polys).groebner_basis(); roots = G[-1].roots()
  ```
- Pitfalls: degree miscount (off-by-one in update order) yields UNSAT/empty variety;
  modular inverses of `(s_i+u_i)` need `gcd == 1` check; multiple `(x, coeffs)` roots are
  normal — disambiguate by predicting a held-out token, not by root size.
- Sources: https://tang.cat/2024/06/10/R3CTF-2024-Crypto-Writeup.html ,
  https://ctftime.org/writeup/37984 , https://systemslibrarian.github.io/crypto-lab-nonce-lattice/

### W15 — Crafted nonce-collision reuse (faulted / malleable nonce input)
- Condition: signer hashes attacker-influenced `nonce` input into `k` (e.g. `k` derived
  from user string), so two distinct inputs can be crafted to the same `k`
  (e.g. `00` vs `0000` normalize identically); two signatures then share `r`.
- Steps: 1. Probe normalization: submit candidate pairs, compare returned `r` bytes
  exactly. 2. On collision, sign two different messages, apply reuse closed form
  `k = (z1-z2)*inv(s1-s2)`, `d = (s1*k-z1)*inv(r)`. 3. Verify `d*G == Pub`, then use `d`
  for the real objective (decrypt `d*F`-style point or forge).
- Snippet: ```python
  k = (z1-z2) * pow(s1-s2, -1, q) % q
  d = (s1*k - z1) * pow(r, -1, q) % q
  assert d*G == Pub  # curve multiply check, not string compare
  ```
- Pitfalls: `r` must match byte-exactly (same `k`, not just same length); hash function
  over the message (`md5` vs `sha256`, truncation) changes `z`; some oracles rate-limit
  signing — batch probes, cache every `(input, r, s)`.
- Sources: https://berliangabriel.github.io/post/bi0s-ctf-2024/ ,
  https://ctftime.org/writeup/31821 , https://ctfpal.com/tools/biased-nonce-lattice-attack

### W16 — Anomalous-curve Smart attack (order equals field prime)
- Condition: `E(F_p)` with `#E == p` (anomalous); Sage `E.order() == p`. ECDLP lifts to
  a `p`-adic logarithm — polynomial time, no lattice.
- Steps: 1. Confirm `E.order() == p` in Sage (do NOT attempt generic DLP first).
  2. Lift points to `p`-adic field, apply Smart's map (`p`-adic log of the lifted
  x-coordinate ratio), solve linear equation for `d`. 3. Verify `d*G == Pub` on the
  original curve.
- Snippet: ```python
  # Sage: E = EllipticCurve(GF(p), [a,b]); assert E.order() == p
  # Eq = E.change_ring(Qp(p, prec=8)); Pq, Gq = Eq(P), Eq(G)
  # d = (p-adic log ratio per Smart script); verify d*G == P over GF(p)
  ```
- Pitfalls: curve-point validation gaps often accompany this (invalid `x` accepted) —
  confirm you attack the curve the oracle actually uses; precision too low in `Qp`
  gives wrong lift; MOV (pairing) vs Smart confusion wastes hours — check `order == p`
  first, pairing order second.
- Sources: https://ctftime.org/writeup/21941 , https://ctftime.org/writeup/18698 ,
  https://ctftime.org/writeup/25665

### W17 — DSA/DH parameter-tampering checklist (validation gaps)
- Condition: server accepts client-supplied or challenge-supplied `(p, q, g)` / curve
  params without validation (non-prime `q`, smooth `p-1`, small-order `g`, `g = 1` or
  `g = p-1`, reused `(p, g)` across sessions).
- Steps: 1. Factor `p-1` (trial + Pollard-rho + ECM, timeout-bounded) and compute element
  orders of `g`. 2. If a small subgroup exists, force shared secret into it
  (send `y = g^small` / small-order public value) and brute-force the subgroup.
  3. Confirm by decrypting one known-structure message before scaling the attack.
- Snippet: ```python
  import sympy
  fac = sympy.factorint(p-1)          # timeout-bounded; smooth => Pohlig-Hellman
  for prime, _ in fac.items():
      if pow(g, (p-1)//prime, p) == 1:
          print('small subgroup order divides', prime)
  ```
- Pitfalls: `g = p-1` gives order-2 confinement (1-bit secret) — check trivial cases
  before lattice/BSGS; some checks need the peer's public value replayed exactly;
  `q` non-prime breaks DSA-nonce math silently — validate `q` primality first.
- Sources: https://ctftime.org/writeup/25665 , https://ctftime.org/writeup/30186 ,
  https://ctftime.org/writeup/33861

### W18 — ElGamal/DH small-subgroup confinement plus Lim-Lee
- Condition: DH/ElGamal over prime `p` with smooth `p-1` and missing subgroup check;
  static-key server reuses private exponent (needed for active Lim-Lee across sessions).
- Steps: 1. Map smooth factors of `p-1`; craft public keys of small order per factor
  (Lim-Lee active attack), recover secret mod each factor via oracle responses.
  2. CRT-combine residues to full secret. 3. Passive variant: Pohlig-Hellman on a
  captured transcript when randomness is weak.
- Snippet: ```python
  # per smooth factor l: send h of order l, learn secret mod l from decapsulation
  # residues = [(s_i, l_i), ...]; secret = crt(residues)  # sympy ntheory crt
  ```
- Pitfalls: needs static key + responsive oracle per factor (noisy services need
  retry/majority per residue); validate each residue (`h^secret` consistency) before CRT;
  ephemeral-only deployments are NOT vulnerable — confirm key reuse first.
- Sources: https://ctftime.org/writeup/37362 , https://ctftime.org/writeup/30186 ,
  https://ctftime.org/writeup/33861

## Symmetric / hash family

### W19 — CBC-R encrypt-via-decrypt-oracle (second gate after H6)
- Condition: padding oracle already yields intermediate bytes `I` for a target block
  (H6 done); goal is a VALID ciphertext for chosen plaintext, not just decryption.
- Steps: 1. Finish one-block decrypt, keep `I`. 2. Forge `C_prev' = I ^ want` for each
  block from last to first (random first `C_0'`, IV' = `I_0 ^ want_0`). 3. Submit forged
  token exactly once; random-token control must fail.
- Snippet: ```python
  def cbc_encrypt_block(inter, want, nblocks=1):
      import os
      forged = [bytes(a ^ b for a, b in zip(inter[i], want[i])) for i in range(nblocks)]
      return forged  # prepend random C0' + set IV' = inter[0]^want[0] for block 0
  ```
- Pitfalls: `want` must be block-aligned with correct PKCS#7 padding bytes included;
  reusing the SAME `C_prev'` twice leaks `I` structure — one-shot per target;
  services that bind IV server-side need the IV-variant path, not `C_prev` path.
- Sources: https://ctftime.org/writeup/40337 , https://ctftime.org/writeup/27084 ,
  https://ctftime.org/writeup/36012

### W20 — CBC-MAC concatenation / length-extension forgery
- Condition: `MAC = CBC-MAC_k(msg)` with variable-length messages and no length prefix
  (or prefix parsed after MAC check); attacker holds one valid `(msg, tag)` pair.
- Steps: 1. Request MAC of `msg1`, get `t1`. 2. Forgery for `msg1 || (msg2 ^ t1)` equals
  MAC of the concatenation — submit without ever learning `k`. 3. If a length field
  exists but is attacker-controlled, recompute it for the spliced message.
- Snippet: ```python
  def xor(a: bytes, b: bytes) -> bytes:
      return bytes(x ^ y for x, y in zip(a, b))
  forged_msg = msg1 + xor(msg2, tag1)  # tag of forged_msg == tag of (msg1||msg2) chain
  ```
- Pitfalls: fixed-length-only MACs resist this — confirm variable length first;
  block-alignment must be exact (pad `msg1` to block boundary before splicing);
  truncated tags need the truncation applied AFTER the algebra, not before.
- Sources: https://ctftime.org/writeup/39063 , https://ctftime.org/writeup/37748 ,
  https://ctftime.org/writeup/27084

### W21 — GCM GHASH forgery under nonce reuse
- Condition: AES-GCM with a repeated `(key, nonce)` across two messages (tag/length
  pairs observable); goal is a valid tag for a forged ciphertext, not key recovery.
- Steps: 1. From two same-nonce pairs derive GHASH polynomial equation in `H`
  (difference of tags cancels keystream, leaves `H`-polynomial). 2. Root-find `H` over
  `GF(2^128)` (Sage `GF(2^128, 'x')` with GCM modulus). 3. Forge tags for arbitrary
  ciphertext with recovered `H`; verify one forgery before chaining.
- Snippet: ```python
  # Sage: F.<x> = GF(2^128, modulus=x^128+x^7+x^2+x+1)  # GCM field
  # build D(H) = T1 - T2 - GHASH_diff(C1, C2, H) == 0 ; H = D.roots()[0][0]
  ```
- Pitfalls: GCM field bit-reflection (the `reverse` convention) flips every root —
  test both conventions against a known tag; short tags (32/64-bit) need the truncation
  modeled in the equation; single-nonce-use deployments need a different path.
- Sources: https://ctftime.org/writeup/39572 , https://ctftime.org/writeup/37748 ,
  https://ctftime.org/writeup/26871

### W22 — Hash length-extension with keylen differential detection
- Condition: `MAC = H(secret || msg)` with MD5/SHA1/SHA256 (Merkle-Damgaard), attacker
  can append data and needs valid tag; secret length unknown.
- Steps: 1. Run `hash_extender --table` sweep (or hashpump) over keylen 8..64, generate
  candidate `(forgery, tag)` per keylen. 2. Differential check: submit TWO forgeries at
  adjacent keylens; the oracle's accept/reject pattern identifies true keylen without
  knowing the secret. 3. Confirm with a benign append before the real payload.
- Snippet: ```bash
  hash_extender --data 'orig' --signature '<sighex>' --append '<append>' --secret 14 --format all --table
  # sweep --secret 8..64; keep the keylen whose forgery verifies, discard the rest
  ```
- Pitfalls: SHA256 vs SHA1 vs MD5 padding differs — `--format all` then narrow by
  `hashid`; secret longer than 64 bytes is rare but breaks the sweep (extend range);
  URL-encoding of `append` must match server parsing exactly (re-encode per attempt).
- Sources: https://ctftime.org/writeup/40553 , https://ctftime.org/writeup/40118 ,
  https://ctftime.org/writeup/40488

### W23 — JWT triage ladder (order matters, crack last)
- Condition: JWT accepted by server; test in this order because each step is cheaper
  than cracking: `alg=none` → weak HMAC → `kid` traversal/SQLi → `jku`/`x5u` confusion.
- Steps: 1. Try `alg: none` with empty signature (some libs accept). 2. `hashid` the
  signature entropy; only then `hashcat -m 16500` bounded dict for HMAC secret.
  3. `kid` path traversal (`../../dev/null`, null-byte) and SQLi (`' OR 1=1` key
  lookup). 4. `jku`/`x5u` to attacker URL serving own JWKS; verify forged token once.
- Snippet: ```bash
  hashcat -m 16500 jwt.txt wordlist-top10000.txt --force   # HMAC-SHA256 secret only
  python3 -c "import base64,json; print(json.loads(base64.urlsafe_b64decode('eyJhbGciOiJIUzI1NiJ9'+'==')))"
  ```
- Pitfalls: base64url (no padding) vs base64 mixups invalidate every test — normalize
  first; RS256→HS256 confusion needs the RSA PUBLIC key as HMAC secret (fetch it);
  `kid` SQLi needs error-based confirmation before chaining.
- Sources: https://ctftime.org/writeup/40817 , https://ctftime.org/writeup/39955 ,
  https://ctftime.org/writeup/39392

### W24 — CTR malleability forge without any oracle
- Condition: CTR-mode ciphertext with attacker-influenced plaintext span and a
  decrypting/acting endpoint; NO padding oracle exists (CBC tricks do not apply).
- Steps: 1. Align target bytes to keystream offsets (known-prefix cribs give positions).
  2. Apply `C_new[i] = C[i] ^ orig[i] ^ want[i]` at those offsets only. 3. Submit once;
  a failed parse means misalignment, not wrong key — re-probe alignment.
- Snippet: ```python
  forged = bytearray(ct)
  for i, (o, w) in zip(offsets, zip(orig_span, want_span)):
      forged[i] = ct[i] ^ o ^ w
  ```
- Pitfalls: malleating length/authenticated-data breaks GCM tags (this is CTR-only);
  bit-level vs byte-level offsets differ on packed protocols — confirm with a one-bit
  probe first; reusing the probe ciphertext afterwards voids the negative control.
- Sources: https://ctftime.org/writeup/26871 , https://ctftime.org/writeup/16472 ,
  https://ctftime.org/writeup/11159

## PRNG / sharing / algebraic family

### W25 — MT backward-twist previous-state recovery (predict the past)
- Condition: 624 consecutive MT19937 outputs observed AFTER the unknown target output
  (e.g. key was drawn, then outputs leaked); forward clone alone cannot reach backwards.
- Steps: 1. Untemper the 624 words to current state. 2. Apply inverse-twist (untwist)
  walking indices `N-1 .. 0` with the `MATRIX_A` conditional, per the standard
  untwist routine. 3. Generate backwards/forwards to the target index; confirm against
  one known value at that index before using the recovered key material.
- Snippet: ```python
  # per-index untwist core (N=624, M=397, UPPER_MASK=0x80000000, MATRIX_A=0x9908b0df)
  # tmp = mt[i] ^ mt[(i+M) % N]; result_hi = (tmp << 1) & UPPER_MASK  (+ MATRIX_A undo)
  # see practical-ctf untwist() patch; then offset(-624) to step back one state
  ```
- Pitfalls: Python's `random` reseeds state layout on `seed()` — clone must model the
  exact version's `setstate` tuple `(3, tuple(state+[0]), None)`; outputs from
  `random()` doubles carry only 53 bits (need reconstruction, not raw submit).
- Sources: https://qiita.com/quantum_for_ctf/items/cf15628a596b1641cc53 ,
  https://github.com/JorianWoltjer/practical-ctf/blob/main/cryptography/pseudo-random-number-generators-prng.md ,
  https://pwn.college/cse539-s2025/randomness/

### W26 — Symbolic MT solver for truncated outputs (bit-budget rule)
- Condition: fewer than 624 full words OR truncated outputs (e.g. upper 20 of 32 bits
  over 982 samples); RandCrack/untwist cannot run (needs full words).
- Steps: 1. Model MT state as 624 z3 `BitVec(32)`, add `symbolic_untamper` constraints
  per sample with `?` bits unconstrained, plus `symbolic_twist` relations past index 624.
  2. Rule of thumb: need `samples * known_bits >> 19937` (e.g. 982*20 = 19640, marginal
  — expect partial recovery + brute-force of the remainder). 3. Extract model state,
  rebuild `random.Random` via `setstate`, verify against held-out outputs; brute-force
  leftover bits (e.g. low 12 bits of key bytes) only after the model checks out.
- Snippet: ```python
  from z3 import BitVec, Solver
  MT = [BitVec(f'MT_{i}', 32) for i in range(624)]
  # per sample: solver.add(untamper(MT[idx]) & mask == observed>>shift)
  # past 624: solver.add(MT_next[i] == twist(MT)[i]); check() then setstate
  ```
- Pitfalls: twist modeling is the slow part — cap samples to what the budget needs
  (more samples != faster solve); index-0 anomaly (first word often mismatches) is a
  known artifact — skip index 0 and verify from index 1; solver timeout must be set
  (`s.set('timeout', ...)`), else it hangs past the tier budget.
- Sources: https://medium.com/@random1106/smileyctf2025-neverenough-writeup-109840e1dc2a ,
  https://sinapsi.wiki/w/ctf-crypto/p/stream/prng-prediction/ ,
  https://stackered.com/blog/python-random-prediction/

### W27 — Seed-vs-clone decision (narrow seeds first, inversion second)
- Condition: PRNG output observed but consecutive-word requirement unmet; seed may be
  narrow (timestamp window, PID, small int) OR default OS-seeded (unclonable seed).
- Steps: 1. FIRST try seed brute-force: replay generator per candidate seed in the
  plausible window, match one output (fastest win). 2. If seeded with 32-bit int and a
  few outputs exist, use init-array inversion (few-output recovery, no brute force).
  3. Only then fall back to full clone (W25) or symbolic (W26); CSPRNG
  (`os.urandom`/`secrets`) ends this path immediately — re-triage.
- Snippet: ```python
  import random, time
  for cand in range(t0, t1):  # narrow window only, e.g. ±3600 s around event start
      r = random.Random(cand)
      if r.getrandbits(32) == observed:
          print('seed', cand); break
  ```
- Pitfalls: Python version changes `seed()` → state mapping (version-1 vs version-2
  for str/bytes seeds) — match the challenge's version; `random.seed(a=None)` uses OS
  entropy (never brute-forceable); interleaved draws from the same instance desync
  naive replay — mirror the exact call sequence.
- Sources: https://stackered.com/blog/python-random-prediction/ ,
  https://sinapsi.wiki/w/ctf-crypto/p/stream/prng-prediction/ ,
  https://github.com/JorianWoltjer/practical-ctf/blob/main/cryptography/pseudo-random-number-generators-prng.md

### W28 — Truncated-LCG lattice recovery (few-output state solve)
- Condition: LCG/Java-style PRNG with only top bits per output (e.g. 8-bit draws from
  48-bit state); too few bits for direct algebra, but several consecutive samples exist.
- Steps: 1. Write truncated outputs as `y_i = (a^i*s_0 + c_i) mod m` high-bits-known.
  2. Build hidden-number lattice over the unknown low bits (scale by `2^unknown_bits`),
  LLL-reduce, solve closest-vector for the state. 3. Clone generator (java-random style
  lib), confirm next output exactly before predicting.
- Snippet: ```python
  # Sage sketch: L = lattice from multiplier powers, target = shifted truncations
  # B = L.LLL(); state = Babai_closest(B, target); verify clone predicts next draw
  ```
- Pitfalls: modulus `m` must be exact (Java `2^48` vs glibc `2^31` vs custom) — wrong
  `m` gives plausible-looking wrong states; increment `c` handling differs per
  implementation (additive constant inside vs outside truncation); needs enough samples
  (`samples * known_bits` must clear state bits with margin).
- Sources: https://ctftime.org/writeup/36141 , https://ctftime.org/writeup/23497 ,
  https://github.com/JorianWoltjer/practical-ctf/blob/main/cryptography/pseudo-random-number-generators-prng.md

### W29 — Shamir misuse recipes (threshold, duplicate-x, x=0, forged shares)
- Condition: shares `(x, y)` over known prime field `p`; misuse in one of four shapes:
  (a) threshold set to 1, (b) duplicate `x` with different `y` (inconsistent dealer),
  (c) service evaluates user-supplied `x` (especially `x = 0` = the secret),
  (d) shares unauthenticated (attacker injects own share into reconstruction).
- Steps: 1. Confirm field prime and share encoding (int vs bytes). 2a. Threshold-1:
  any single share IS the secret (verify by reconstruction with random others).
  2b. Duplicate-`x`: the inconsistency itself leaks dealer randomness — solve the two
  evaluations for the polynomial coefficients. 2c. Query `x = 0` directly; if blocked,
  query two adjacent `x` and extrapolate. 2d. Submit crafted share to steer `f(0)`.
  3. Always verify against a held-out share.
- Snippet: ```python
  def lagrange_zero(shares, p):
      s = 0
      for i, (xi, yi) in enumerate(shares):
          num = den = 1
          for j, (xj, _) in enumerate(shares):
              if i != j: num, den = num*(-xj) % p, den*(xi-xj) % p
          s = (s + yi*num*pow(den, -1, p)) % p
      return s
  ```
- Pitfalls: `x` values may be 1-indexed in prose but 0-indexed on the wire — confirm
  with two known shares first; field may be `GF(2^m)` not prime (different Lagrange);
  share compression (only `y` sent, `x` implied by order) misaligns interpolation.
- Sources: https://ctftime.org/writeup/31892 , https://ctftime.org/writeup/19862 ,
  https://ctftime.org/writeup/18602

### W30 — Generalized-GM / Paillier algebraic decrypt (modified-BD equation)
- Condition: RSA-like modulus with structured primes (e.g. low halves fixed to 1) plus
  a residue-symbol decryption rule (Generalized Goldwasser-Micali / Paillier flavor);
  small-`d` hint present but stock Boneh-Durfee fails (wrong `A`).
- Steps: 1. Rewrite modulus with structure (`p = 2^512*p0 + 1` shape) to get reduced
  equation `k*(A - s) + inv(2^512) = 0 (mod e)` with `A = (N - N mod 2^512)/2^512`.
  2. Patch the BD Sage script's polynomial line only (keep lattice params), solve for
  `(k, s)`. 3. Recover `p, q` from `s`, then run the scheme's own decrypt (residue
  algorithm per paper section), verifying prime assignment (`(p-1) mod 2^512 == 0`
  tells which factor is `p`).
- Snippet: ```python
  # in boneh_durfee.sage replace: A = int((N+1)/2); pol = 1 + x*(A+y)
  # with: A = (N - int(N % (2**512))) // 2**512
  #       pol = inverse_mod(2**512, e) + x*(A - y)
  ```
- Pitfalls: stock-script failure is EXPECTED here (not a delta-tuning problem) —
  diagnose via prime structure first; `p`/`q` assignment swap breaks residue decrypt
  silently — use the `(p-1) mod 2^512` test; decryption math differs per scheme
  (read the paper's decrypt section, do not assume textbook RSA decrypt).
- Sources: https://ctftime.org/writeup/22997 , https://ctftime.org/writeup/23495 ,
  https://ctftime.org/writeup/18602
